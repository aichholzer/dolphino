# Local MVP enhancements — September 2026

The overview offers 1, 2, 3, 4 and 6 calendar months ending in the selected month. Aggregate figures and each monthly comparison retain contributing-transaction drilldowns, with the current month marked partial. Category budgets remain monthly. Account labels and descriptions are local overrides; opening a card shows its paginated history with adjustable dates. All accounts continue syncing and contributing to reports. There is no account-disable feature.

Settings support encrypted OpenAI or Amazon Bedrock configuration, manual model identifiers, bounded classification and explicit opt-in automatic application. Bedrock supports permanent access keys only and uses a maintained commercial-region catalogue, defaulting to Sydney; a listed region is not a promise that a model is available there. Connection checks are read-only. Explicit model tests use synthetic data, may incur a small inference charge, and have their own five-per-minute limit, separate from the daily classification allowance. Bedrock model invocation requires an already authorized, available model and never provisions access or subscribes to Marketplace products. See [providers](providers.md).

Secrets are write-only and encrypted with versioned AES-256-GCM envelopes, random salt and nonce, domain-separated HKDF, and setting/provider binding. Blank fields preserve values; explicit clear removes them. Missing/wrong `APP_SECRET` prevents credential use while stored financial data stays usable. Save the master key separately from database backups and use the documented transactional [key rotation procedure](settings-security.md).

Authenticated live settings can register/reuse a Redbark thin-event destination after a successful connection test. This is separate from full-data destinations and sync configuration. Registration preserves durable intent and encrypted signing secrets and requires explicit recovery if the one-time secret was lost. The callback must be publicly reachable HTTPS without interactive login; only its narrow callback path should bypass an external login layer. See [Redbark](redbark.md) and [import health/backfill](import-health.md).

Optional Telegram and SMTP notifications use a durable outbox sourced from atomic alert open, resolve and reopen transitions. Default summaries contain category, period, amount and remaining status; users may choose which of these fields to include. Transaction descriptions and account identifiers are never included. Telegram uses a dedicated bot, a private household group managed by the household, an expiring pairing command and explicit group confirmation. Existing bot webhooks are never replaced. SMTP requires verified TLS, From and recipient addresses. Credentials remain encrypted; test actions name their configured destination. See [notifications](notifications.md).

## Verification boundaries

All development credentials, ledger records and provider responses are synthetic. No Redbark registration, bot creation, Telegram send, email send, Bedrock/OpenAI inference or real financial import was performed. Provider access, model availability, SMTP sender verification, public HTTPS reachability and actual bank freshness must be checked by the owner on their own deployment. Automated tests mock external services and use disposable local PostgreSQL schemas/databases.

The application is a single-user authenticated service. A shared Telegram group distributes alerts to household members; it does not add application users or manage group membership. Delivery retries cannot guarantee exactly-once external delivery when a provider accepts a message but the response is lost. Failed or uncertain delivery states remain visible for review. Group migrations require a fresh explicit pairing. No push or deployment was performed.

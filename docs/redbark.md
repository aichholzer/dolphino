# Redbark connection

Profe supports the **v2 thin event destination** contract and read-only v2 bank transaction APIs. No live calls were used in development. Redbark v2 is beta; its documentation currently names `2026-10-01.wattle`. That is a documentation default, not an assertion that your account can use it. Configure the release and run **Test connection** before imports are enabled. The successful test is bound to the API key/version fingerprint; changing either requires another test. Source: [v2 overview](https://redbark.com/docs/api-reference/v2/overview).

Configure `REDBARK_API_KEY` and `REDBARK_WEBHOOK_SECRET` only on the server (or corresponding `_FILE` Docker secrets), `REDBARK_VERSION`, and `REDBARK_BACKFILL_DAYS` (default 90, maximum 2555). Use live mode with authentication configured and a dedicated live database. Never paste credentials into chat or the browser. The UI only exposes configuration presence and safe status codes. Use a key with `data:read`. Profe does not create destinations, change syncs, or ask for write scopes.

In your Redbark dashboard create an **event destination**, pointing to your HTTPS `/api/webhooks/redbark` endpoint. Subscribe to `transactions.synced`, `connection.*`, and `sync_run.succeeded`. Keep its signing secret server-side. Configure your reverse proxy to preserve the exact request bytes and `Redbark-Signature` header. The receiver validates timestamped HMAC-SHA256, accepts rotated signatures, and rejects signatures outside five minutes. Synchronize the server clock. An event ID and raw bytes are committed with its work item before acknowledgement. Replays deduplicate; conflicting bytes for an existing ID are rejected. Processing is asynchronous, restart-safe and serialized across workers using PostgreSQL advisory locks. Source: [thin events](https://redbark.com/docs/api-reference/v2/events).

Every four hours Profe rediscovers accounts and imports the configured rolling date window, including pending rows separately from posted actuals. Events queue the same discovery/import procedure; event URLs are never followed. All discovered banking accounts are included, so no Profe-maintained explicit webhook account list can become stale. If you separately use account-limited Redbark syncs, update their coverage yourself when adding accounts. No connection refresh is sent: refresh queues enabled syncs and cannot guarantee new bank activity. `transactions.synced` describes sync output, not an instantaneous card-use notification.

Reads use one account, at most 100 rows per page and explicit inclusive dates. A truncated response restarts the window in smaller nonoverlapping calendar ranges. A single truncated day fails visibly; no complete coverage is claimed. Imports repeatedly cover the configured window, recovering overlap and late changes within it. Increase backfill days explicitly to revisit older changes. Brokerage holdings/trades are outside this MVP. Source: [transaction reads](https://redbark.com/docs/api-reference/v2/transactions/list-transactions).

Failures retain durable jobs and retry with exponential delay, honoring `Retry-After`; provider error bodies are not logged or returned. Database outages never switch database targets. Raw responses and fetch times remain evidence, while canonical IDs, overrides and audit history belong to the finance store. Provider categories are retained, with Profe rules/corrections independent. Balance snapshots retain source observation time and current balance type; absence of a compatible opening balance and coverage is shown as not reconciled. Source: [balance API](https://redbark.com/docs/api-reference/v2/accounts/retrieve-the-account-balance).

**Full transaction webhooks are unsupported.** They use `X-Redbark-Signature` plus `X-Redbark-Timestamp`, `data.new`/`data.updated`, raw transaction IDs and `account_public_id`. They cannot be safely mixed with tagged v2 transaction IDs by simply comparing strings. Their three-attempt retry/disable behavior differs sharply from thin events' multi-day retries. Do not select a full webhook destination for Profe. Source: [full webhook contract](https://redbark.com/docs/api-reference/webhooks).

Pending IDs may change at posting. Do not deduplicate transactions by amount/date/merchant alone: genuine identical purchases must survive. Ambiguous pending replacements need human review; posted-only actuals exclude unresolved pending observations. Source: [sync behavior](https://redbark.com/docs/syncs).

The integration's mock tests cover signatures, replay age, raw bytes, rotation, pagination, truncation, rate limits and exact amounts. Real availability, account scopes and bank/provider behavior remain for your test connection and first monitored import. Inspect Settings after the first import and check coverage, source timestamps and the review queue before relying on totals.

## Classification evidence and dates

Documented provider codes `TRANSFER_IN`/`TRANSFER_OUT` initialize transfer kind, with review to confirm they represent your own transfers or card repayments. `INCOME` initializes positive income. A credit retaining a recognized spending category initializes a **provisional refund** and requires review. `LOAN_PAYMENTS` needs review because principal, interest and card repayments have different meanings. Unknown codes and category-less transactions require review; custom category labels alone never prove transaction kind. Rules and manual corrections take precedence. There is no documented v2 refund/type flag, so Profe does not invent one. [Provider category vocabulary](https://redbark.com/docs/api-reference/transactions#categories).

Posted rows use `post_date` when provided, otherwise the provider's transaction `date`; pending rows use transaction date. Refunds therefore affect their booking month when available, with the same documented fallback. Configure Redbark's account timezone to match Profe (`Australia/Brisbane` by default): provider calendar dates are retained without guessing timezone conversions. The raw date fields remain in evidence.

## Register from Settings

With live authentication, a tested server-side Redbark API key, and a strong `APP_SECRET`, enter the public HTTPS **origin** in Settings (for example `https://finance.your-domain.net`) and explicitly select Register. Profe registers `/api/webhooks/redbark` as a **thin event destination**, subscribing to `sync_run.succeeded` and `connection.refreshed`. It does not create a full transaction destination or a bank sync. Configure enabled bank syncs in Redbark; the registration status states this coverage limitation. Existing four-hour discovery/reconciliation remains active.

Only public DNS names resolving to public addresses are accepted; credentials, paths, query strings, nonstandard ports and IP literals are rejected. Profe never fetches the callback URL or follows event-provided URLs. All provider requests use the fixed Redbark v2 origin and reject redirects. The endpoint must be reachable by Redbark without interactive login. If using Cloudflare Access, create a narrow exception for `/api/webhooks/redbark` only; keep the UI protected. HMAC verification and timestamp replay protection remain mandatory; do not rely on a source-IP allowlist.

Registration needs the API key's `events:write` permission plus permission to list destinations. No permission changes are made by Profe. The beta API version must actually pass your connection test before integration is enabled; a documented future version is not proof of availability.

A database advisory lock serializes registration. Profe saves a durable intent before remote creation, finds an existing destination by exact callback URL, and atomically stores its ID with its encrypted one-time signing secret. Repeated Register calls reuse it. Multiple remote matches require manual cleanup. If a crash loses a one-time create response, a retry detects the existing destination and requests explicit signing-secret recovery rather than creating another. The recovery control invokes Redbark's documented rotation endpoint, encrypts the new secret, and stores it atomically. The provider allows the old signing secret for 24 hours; Profe verifies with the newest stored key. If rotation's response is lost, repeat explicit recovery. A URL change requires manual cleanup of the previous registration before changing the local registration row; it never silently leaves a second remote subscription.

Test sends a synthetic provider ping. A queued ping is **not** proof of successful delivery: Settings reports receipt only when its event ID exists in the durable webhook receipt table. Signing secrets, API keys and signatures are never included in Settings responses. Missing or wrong `APP_SECRET` stops credential-dependent operations while stored-data access remains available.

Contract references: [thin events and destinations](https://redbark.com/docs/api-reference/v2/events), [create destination](https://redbark.com/docs/api-reference/v2/event-destinations/create-an-event-destination), [public webhook requirements](https://redbark.com/docs/webhook). No destination was registered during development; all registration tests use mocked Redbark responses and synthetic secrets.

An event can arrive immediately after remote creation, before local secret storage completes. Profe returns 503 until it can verify the key; Redbark retries. For reused destinations, the recovered key is saved before updating subscriptions or re-enabling delivery.

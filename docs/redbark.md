# Redbark connection

dolphino supports the **v2 thin event destination** contract and read-only v2 bank transaction APIs. No live calls were used in development. Redbark v2 is beta; its documentation currently names `2026-10-01.wattle`. That is a documentation default, not an assertion that your account can use it. Configure the release and run **Test connection** before imports are enabled. The successful test is bound to the API key/version fingerprint; changing either requires another test. Source: [v2 overview](https://redbark.com/docs/api-reference/v2/overview).

In administrator **Settings → Bank feeds → Redbark**, save the write-only API key, API version and rolling backfill days (default 90, range 1–2555). Use live mode with authentication configured and a dedicated live database. Changes take effect immediately without a restart. Use a key with `data:read` for imports. Settings can explicitly create/reuse a thin event destination using `events:write` and destination-list permission; dolphino does not change key permissions or provision Redbark syncs. Its one-time signing secret is encrypted with `APP_SECRET`. To keep a manually configured destination, enter its secret in the write-only **Existing destination signing secret** field. Blank secret fields preserve saved values; **Clear** explicitly removes a value when saved. Never paste credentials into chat.

Redbark configuration is database-only. Legacy environment values are ignored, including `_FILE` variants; there is no automatic import or fallback. Existing environment-only users must re-enter their settings explicitly. A previously encrypted registration secret stays stored in its existing slot. Changing the API key suspends that secret’s association until the matching destination is registered/recovered or its secret explicitly re-entered. Missing/unreadable credentials pause the affected integration without deleting imports, overrides, receipts or queued jobs. See the [upgrade checklist](database-integration-upgrade.md).

Settings registration subscribes to exactly **`sync_run.succeeded` and `connection.refreshed`** at the public HTTPS `/api/webhooks/redbark` endpoint. These are thin-event notifications that trigger reconciliation, not a live bank-feed subscription. `sync_run.succeeded` requires an existing Redbark sync to run successfully; registering this endpoint creates no such sync. `connection.refreshed` describes connection re-materialisation and is not a per-transaction notification. Without an existing sync, do not expect sync-run events. Neither event guarantees instant new bank activity. Source: [thin events and event definitions](https://redbark.com/docs/api-reference/v2/events).

Both subscribed event types enqueue the same account-discovery and REST import procedure for all accessible supported accounts and the configured rolling date window. Event URLs are never followed. A synthetic `event_destination.ping` is stored as a verified receipt without importing transactions. Configure the reverse proxy to preserve exact request bytes and `Redbark-Signature`. dolphino validates timestamped HMAC-SHA256 and rejects signatures outside five minutes; synchronize the server clock. Event ID, raw bytes and import job are committed before acknowledgement. Replays deduplicate; conflicting bytes for an existing ID are rejected. Processing is asynchronous and serialized across workers using PostgreSQL locks.

**Independent four-hour polling remains the fallback even if no thin events arrive or no destination is registered.** While the process runs with successfully verified API key/version configuration, a fifteen-second scheduler queues one durable poll job per four-hour time bucket. Provider/database outages, Retry-After, queued work and process downtime can delay execution; this is not a guarantee of fresh bank data every four hours. Polling rediscovers accounts and reads balances and transactions already available through Redbark. It does not force a bank refresh. All discovered banking accounts are included. Owners maintain coverage of any separate account-limited Redbark syncs. `transactions.synced` is not subscribed by Settings; it describes sync output rather than instantaneous card use.

Reads use one account, at most 100 rows per page and explicit inclusive dates. A truncated response restarts the window in smaller nonoverlapping calendar ranges. A single truncated day fails visibly; no complete coverage is claimed. Imports repeatedly cover the configured window, recovering overlap and late changes within it. Increase backfill days explicitly to revisit older changes. Redbark limits banking history to about seven years: a rolling window of 2555 days was rejected with HTTP 400, while 2500 days was accepted. Brokerage holdings/trades are outside this MVP. Source: [transaction reads](https://redbark.com/docs/api-reference/v2/transactions/list-transactions).

Failures retain durable jobs and retry with exponential delay, honoring `Retry-After`. A stored error names the request and keeps only Redbark's machine-readable error code and parameter, for example `provider_http_400 on transactions: parameter_invalid (from)`. Messages, request IDs, account IDs and response bodies are discarded. An account whose balance or transactions request is refused with 400, 403, 404, 409 or 422 is skipped and named in the status, and the other accounts still import. If every account is refused, the job fails and retries. Rate limits, provider outages and credential failures stop the whole sync and back off. Database outages never switch database targets. Raw responses and fetch times remain evidence, while canonical IDs, overrides and audit history belong to the finance store. Provider categories are retained, with dolphino rules/corrections independent. Balance snapshots retain source observation time and current balance type; absence of a compatible opening balance and coverage is shown as not reconciled. Source: [balance API](https://redbark.com/docs/api-reference/v2/accounts/retrieve-the-account-balance).

**Full transaction webhooks are unsupported.** They use `X-Redbark-Signature` plus `X-Redbark-Timestamp`, `data.new`/`data.updated`, raw transaction IDs and `account_public_id`. They cannot be safely mixed with tagged v2 transaction IDs by simply comparing strings. Their three-attempt retry/disable behavior differs sharply from thin events' multi-day retries. Do not select a full webhook destination for dolphino. Source: [full webhook contract](https://redbark.com/docs/api-reference/webhooks).

Pending IDs may change at posting. Do not deduplicate transactions by amount/date/merchant alone: genuine identical purchases must survive. Ambiguous pending replacements need human review; posted-only actuals exclude unresolved pending observations. Source: [sync behavior](https://redbark.com/docs/syncs).

The integration's mock tests cover signatures, replay age, raw bytes, rotation, pagination, truncation, rate limits and exact amounts. Real availability, account scopes and bank/provider behavior remain for your test connection and first monitored import. Inspect Settings after the first import and check coverage, source timestamps and the review queue before relying on totals.

## Classification evidence and dates

In API v2, transaction `category` is an opaque `cat_…` reference. dolphino reads every page of `GET /v2/categories` and resolves that reference to its `name`; the original reference and bank `provider_category` remain in immutable source evidence. Custom taxonomy reads need `categories:read` in addition to `data:read`. Missing permission does not stop bank imports: **Import health & history** shows a warning, known category names remain, and unresolved references display **Uncategorized**. A category lookup rate limit still honors provider backoff. [Category taxonomy and scope](https://redbark.com/docs/api-reference/v2/syncs#categories).

Each verified import also reconciles derived category labels for all already-imported history of the direct-Redbark accounts it processes, including dates outside the rolling fetch window. This repairs earlier imports that stored category IDs as labels. The reconciliation uses matching retained bank evidence and preserves amounts, dates, transaction identity and kind, manual corrections/splits, rule precedence, accepted AI fields and source-identity warnings. Category-only changes are audited and repeated runs are idempotent. It does not rewrite user-authored budget/rule categories or manual correction values, and it cannot repair accounts no longer accessible to that connection. No transaction re-download or destructive migration is needed for this label repair.

Documented provider codes `TRANSFER_IN`/`TRANSFER_OUT` initialize transfer kind, with review to confirm they represent your own transfers or card repayments. `INCOME` initializes positive income. A credit retaining a recognized spending category initializes a **provisional refund** and requires review. `LOAN_PAYMENTS` needs review because principal, interest and card repayments have different meanings. Unknown codes and category-less transactions require review; custom category labels alone never prove transaction kind. Rules and manual corrections take precedence. There is no documented v2 refund/type flag, so dolphino does not invent one. [Provider category vocabulary](https://redbark.com/docs/api-reference/transactions#categories).

Review is a queue of uncertain records, not a view of every import. Provider transfer candidates are deliberately queued while ordinary categorized expenses usually are not. Review rows display the exact signed amount and currency, date, account, category and current type; use the original evidence when deciding whether a transfer is internal. The category-name repair does not reinterpret transfers or change their treatment in totals.

Posted rows use `post_date` when provided, otherwise the provider's transaction `date`; pending rows use transaction date. Refunds therefore affect their booking month when available, with the same documented fallback. Configure Redbark's account timezone to match dolphino (`Australia/Brisbane` by default): provider calendar dates are retained without guessing timezone conversions. The raw date fields remain in evidence.

## Register from Settings

With live authentication, a tested Redbark API key saved in Settings, and a strong `APP_SECRET`, enter the public HTTPS **origin** in Settings (for example `https://finance.your-domain.net`) and explicitly select Register. dolphino registers `/api/webhooks/redbark` as a **thin event destination**, subscribing to `sync_run.succeeded` and `connection.refreshed`. It does not create a full transaction destination or a bank sync. An existing Redbark sync is required to produce `sync_run.succeeded`; `connection.refreshed` is not a per-transaction signal. Configure any desired syncs separately in Redbark. Independent four-hour polling remains the fallback, subject to verification, availability and backoff.

Only public DNS names resolving to public addresses are accepted; credentials, paths, query strings, nonstandard ports and IP literals are rejected. dolphino never fetches the callback URL or follows event-provided URLs. All provider requests use the fixed Redbark v2 origin and reject redirects. The endpoint must be reachable by Redbark without interactive login. If using Cloudflare Access, create a narrow exception for `/api/webhooks/redbark` only; keep the UI protected. HMAC verification and timestamp replay protection remain mandatory; do not rely on a source-IP allowlist.

Registration needs the API key's `events:write` permission plus permission to list destinations. No permission changes are made by dolphino. The beta API version must actually pass your connection test before integration is enabled; a documented future version is not proof of availability.

A database advisory lock serializes registration. dolphino saves a durable intent before remote creation, finds an existing destination by exact callback URL, and atomically stores its ID with its encrypted one-time signing secret. Repeated Register calls reuse it. Multiple remote matches require manual cleanup. If a crash loses a one-time create response, a retry detects the existing destination and requests explicit signing-secret recovery rather than creating another. The recovery control invokes Redbark's documented rotation endpoint, encrypts the new secret, and stores it atomically. The provider allows the old signing secret for 24 hours; dolphino verifies with the newest stored key. If rotation's response is lost, repeat explicit recovery. A URL change requires manual cleanup of the previous registration before changing the local registration row; it never silently leaves a second remote subscription.

Test sends a synthetic provider ping. A queued ping is **not** proof of successful delivery: Settings reports receipt only when its event ID exists in the durable webhook receipt table. Signing secrets, API keys and signatures are never included in Settings responses. Missing or wrong `APP_SECRET` stops credential-dependent operations while stored-data access remains available.

Contract references: [thin events and destinations](https://redbark.com/docs/api-reference/v2/events), [create destination](https://redbark.com/docs/api-reference/v2/event-destinations/create-an-event-destination), [public webhook requirements](https://redbark.com/docs/webhook). No destination was registered during development; all registration tests use mocked Redbark responses and synthetic secrets.

An event can arrive immediately after remote creation, before local secret storage completes. dolphino returns 503 until it can verify the key; Redbark retries. For reused destinations, the recovered key is saved before updating subscriptions or re-enabling delivery.

For existing opaque category references, use [Repair category names](category-repair.md) in Import health. This checks taxonomy without downloading bank history. Ambiguous saved manual references are preserved for an explicit category choice; no database wipe is needed.

## Credential-format upgrades

Only version 3 encrypted credentials are readable. If an API key or signing secret uses a retired format, it stays stored but cannot be used, even with the original APP_SECRET. Explicitly replace the API key and test the saved connection. Replacing it invalidates the existing webhook binding: supply the matching signing secret as well, or explicitly register/recover the intended destination. Blank fields preserve old ciphertext and cannot restore delivery. Existing financial history, webhook receipts and queued jobs remain stored; jobs whose credential account cannot be proven stay paused. Follow [the complete upgrade checklist](upgrading.md) before restoring external access.

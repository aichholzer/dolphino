# Encrypted settings and recoverability

Redbark API keys, destination signing secrets and other provider credentials are encrypted in PostgreSQL with AES-256-GCM. Every new write creates a version 3 envelope containing a fresh random 32-byte salt, 12-byte nonce, ciphertext and 16-byte authentication tag. HKDF-SHA256 derives a separate 256-bit encryption key from APP_SECRET and the salt using a Dolphino-specific version 3 context. Authenticated associated data binds ciphertext to the Dolphino version, exact setting name and provider. Salt, nonce, tag and encoding lengths are validated before decryption. This is reversible encryption, separate from account-password hashing; the running server must decrypt a credential to use it.

**Only version 3 envelopes are readable. Versions 1 and 2 are deliberately rejected**, even with their original APP_SECRET. Unreadable ciphertext is retained, not silently deleted or converted; old AI rows are removed only after an explicit successful shared-connection resolution, including any deliberate clearing. This is a breaking credential-format boundary, not a financial schema reset. Imported financial data, corrections, users, grants, sessions, durable jobs, receipt history, notification configuration and outbox records remain stored. Follow [the upgrade and provider-specific recovery instructions](upgrading.md) before deploying over an existing database.

For a new installation, generate a random 32-byte master secret outside the database and repository, for example `openssl rand -base64 32`, then configure `APP_SECRET` or `APP_SECRET_FILE`. Input must be at least 43 characters and not a low-diversity placeholder. Keep the current secret when upgrading an existing installation; generating another one does not recover retired ciphertext and would make currently readable rows unavailable too. Protect the key separately from PostgreSQL backups and retain the matching application version and key for each backup. Losing the key permanently loses access to its encrypted credentials; imported transactions and corrections remain usable. A changed, absent or incorrect key never activates environment credential fallback.

Secret writes are write-only: omit a field or send an empty string to retain its ciphertext; send `null` to clear it; send a new nonempty value to replace it. A blank save therefore retains an unreadable retired envelope too; it cannot resolve a pending shared-AI migration conflict, which requires a readable profile choice, complete re-entry or an explicit clear of the required credentials. Public settings expose configured/masked state without plaintext or last characters; configured does not imply readable. Notification settings additionally expose `credentialsAvailable` so an unavailable saved credential can be explained in the UI. Invalid writes and enabling with unreadable required credentials fail closed and roll back the provider save. PostgreSQL is the sole integration configuration source; former integration environment variables are ignored, never imported or used as a fallback.

Ordinary saves apply immediately without a server restart. Disabling an integration retains its ciphertext. Classification and assistant share one provider/region and encrypted `ai.*` credential set, with separate model, enablement and limit documents. A changed shared provider, region or credential pauses both features; a provider change clears incompatible model selections and resets assistant sharing acknowledgement, while same-provider key/region changes retain models, consent and limits. A compatible readable version 3 legacy profile can be consolidated transactionally, but conflicts and unreadable profiles require explicit administrator resolution. The app never decrypts or migrates retired version 1/2 formats. See [shared AI settings](ai-settings.md). Redbark API-key replacement invalidates the webhook signing-secret association, requiring deliberate signing-secret configuration or registration/recovery. Telegram token replacement or clearing removes the local pairing. SimpleFIN cannot replace a configured Access URL in place: explicitly disconnect before claiming a new one-use token, and heed its unsupported historical relinking boundary. See [upgrade recovery](upgrading.md#recover-saved-integrations-explicitly).

Unconfigured or unreadable integrations stay paused or fail their credential-dependent operation closed. Ordinary settings may be inspected and disabled without a working encryption key. Credential writes and external registration must pass encryption readiness first. Authentication, exact Origin validation and endpoint rate limiting are API boundaries; decryption errors intentionally omit underlying crypto details and values.

## Explicit offline key rotation

Changing APP_SECRET alone does **not** rotate ciphertext. Rotation is only for credentials already readable by the current version. It decrypts every stored credential, including disabled provider slots, and rejects retired version 1/2 rows; one unreadable row rolls back the entire transaction. Explicitly replace or clear every retired/unreadable credential before attempting rotation. The command does not recover or automatically migrate retired formats.

Stop every dolphino application and worker process and keep them stopped throughout rotation. Back up the database and old key separately; create a new random key in a separately protected file. Provide explicit `PGHOST`, `PGPORT`, `PGDATABASE`, `PGUSER`, `PGPASSWORD`/`PGPASSWORD_FILE` and `PGSSLMODE` settings for the intended installation, then run:

```sh
APP_SECRET_FILE=/run/secrets/old-app-secret NEW_APP_SECRET_FILE=/run/secrets/new-app-secret node scripts/rotate-settings-key.mjs
```

The command holds an exclusive table lock and decrypts/re-encrypts all credential rows in one transaction, writing version 3 envelopes. Authentication or format failure rolls back all changes; success prints only the row count. After success, install the new key as the application's APP_SECRET/APP_SECRET_FILE, restart and inspect settings availability before any explicitly requested provider test. Preserve the old key with pre-rotation backup records and the new key with post-rotation records, separately from database dumps. Before commit the old key works; after commit the new key works. Roll back using the matching backup, key and application version, following [safe restore guidance](deployment.md#export-backup-and-restore). There is no dual-key deployment mode.

# dolphino security model

This is an engineering self-assessment. It is not a third-party penetration test, a certification or a guarantee that no vulnerability remains. Report vulnerabilities as described in [SECURITY.md](../SECURITY.md).

## Threat model and boundaries

Protected assets are household financial records, independent account/budget grants, private assistant conversations/reports, integration secrets, invitation/session tokens and the integrity of imported observations/corrections. Threat actors include unauthenticated visitors, a malicious invited member, a viewer trying to become an editor/admin, compromised provider/model responses, hostile financial text, replayed webhooks and a compromised administrator trying to use configurable SMTP as an internal-network probe.

The host/operator, PostgreSQL administrator, process environment and intended household administrator remain trusted for deployment and credential configuration. Administrators have full financial access but cannot browse another user's assistant chats through the application. Granting a budget deliberately grants that category/month/currency's full household summary without underlying bank transactions. External notification audiences are separate from app membership and require explicit administrator acknowledgement. Encrypted credentials protect a database-only disclosure; compromise of the running process plus APP_SECRET defeats that protection.

## Endpoint and role matrix

Exact IDs are still checked inside the facade. Below, “own” means the authenticated server actor, never actor fields from request/model input. Unknown/forbidden object IDs use nondisclosing errors. ## Attack cases and tests

Run these against a disposable database, as described in [testing](testing.md):

```sh
npm run build
node --test --test-concurrency=1 backend/test/security-adversarial.test.mjs backend/test/assistant-adversarial.test.mjs backend/test/assistant-api.test.mjs
```

Chromium must be installed (`CHROMIUM_PATH` overrides the path). The security test starts a local app with real sessions, a scoped ledger and real browser rendering, and does not intercept finance API responses. Provider and model transports are mocked.

Financial exports/reports are JSON; no CSV exporter exists, so spreadsheet CSV-formula execution is not an active output surface. JSON strings may contain leading `=` safely; a future CSV exporter must add explicit formula neutralization. Assistant Markdown is rendered from lexer tokens into an explicit React element allowlist; raw HTML tokens are omitted, decoded entities remain React text, and code stays literal. Model-provided links and images render only their labels/alt text, with no URL attributes or network requests. User messages remain plain text. Authenticated citation downloads are server-generated, regenerated under current permissions and marked as JSON attachments.

The compiled `test:browser:assistant-markdown` suite covers 22 hostile payloads, including HTML/script/SVG/MathML, executable URL schemes, entity-obfuscated URLs, local/remote images, reference links and code-language attribute injection. It asserts no executable DOM, navigation, popups, remote/local tracking fetches or browser storage. Depth, token-count and size limits fall back to escaped plain text. The real HTTP/PostgreSQL `test:browser:assistant-spending` suite separately verifies exact provider text in responses/private chats, anonymous denial, formatted output and unchanged authorized source totals.

## Residual risk

- Dependency audits cover known advisories only. Keep dependencies updated.
- The Docker image runs as a non-root user and ships no credentials or default master key; secrets, dumps and `node_modules` are excluded from the build context.
- Live APP_ORIGIN requires HTTPS and live cookies are Secure; proxy headers never replace session identity. Optional `TRUST_PROXY` resolves client IPs only through explicitly trusted IP/CIDR peers (plus loopback), walking a bounded X-Forwarded-For chain right to left; untrusted peers cannot choose their rate-limit key. The local HTTP server is intended behind a trusted HTTPS reverse proxy. Real TLS termination, certificate renewal, firewall routing, browser HSTS behavior over deployed HTTPS and proxy configuration were not tested. Restrict backend port exposure. App-origin policy is not a network firewall. An untrusted proxy or malformed chain shares the immediate peer’s IP authentication rate bucket. See [trusted proxies](reverse-proxy.md) for the Caddy/cloudflared boundary and deployment checks.
- CSP permits inline styles needed by the UI, but no inline scripts. The allowed application bundle remains trusted. No external scanner, fuzzing campaign, cryptographic formal verification, browser-engine exploit analysis or sustained denial-of-service test has been run.
- Scrypt concurrency and auth/provider budgets bound work; the service still needs normal reverse-proxy connection/body/time limits and host resource monitoring. Limited IP rate controls do not prevent distributed attacks. No MFA/SSO is implemented.
- Public SMTP is a deliberate administrator capability. DNS pinning and TLS reduce SSRF exposure; provider routing changes can cause safe delivery failures. DNS lookup timeout stops awaiting results but cannot necessarily cancel the OS resolver. Notifications are at-least-once; a crash after remote acceptance can duplicate a delivery. An already in-flight external send cannot be recalled.
- Provider entitlements, webhooks and Telegram/SMTP delivery are exercised with mocks only. Provider contract checks do not prove every model or region is compatible. Model prose can be wrong or influenced by untrusted descriptions even when authorization/tool bounds hold; inspect backend-derived citations. Cancellation is best-effort and cannot guarantee no provider cost. No blanket zero-retention claim is made.
- Permission checks cannot erase data already downloaded, screenshots, copied model responses or a response already delivered before revocation. New calls and in-flight assistant/report boundaries recheck access; deployment/process administrators retain host/database access.
- Private chats are temporary process memory, not encrypted persisted history; restart/expiry removes them. APP_SECRET must be backed up separately, trusted backups/access logs must not capture bearer links or sensitive payloads, and SMTP/provider accounts need least-privilege configuration outside this app.

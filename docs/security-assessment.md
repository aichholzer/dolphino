# dolphino isolated adversarial security assessment

**Historical scope:** this record predates the shared-AI settings change. Descriptions of independent classification/assistant credentials and per-form discovery describe that earlier implementation, not current behavior. Current production uses one shared connection, separate feature controls and one model catalog; see [shared AI settings](ai-settings.md) and [its verification record](shared-ai-settings-verification.md). The original dated evidence and counts below are preserved, not claimed as new runs.

Assessment date: 2026-09-30. Scope: this checkout, an ephemeral loopback HTTP app, unique disposable schemas in the isolated test PostgreSQL database, synthetic users/transactions, Chromium and mocked external transports. An independent implementation reviewer performed the additional HTTP/browser probes and SMTP review. This is an engineering adversarial assessment, **not a third-party penetration test, certification or a guarantee that the app is bulletproof**.

No GitHub, bank, Redbark, AWS, OpenAI, Telegram, Brevo, public SMTP host or home-LAN endpoint was probed. No real credentials, financial records, emails or messages were used. DNS and SMTP checks use explicit mocks; the public IP literals in test results never receive connections. No load/destructive scanner was run. Tests create and drop only their own random PostgreSQL schemas.

## Threat model and boundaries

Protected assets are household financial records, independent account/budget grants, private assistant conversations/reports, integration secrets, invitation/session tokens and the integrity of imported observations/corrections. Threat actors include unauthenticated visitors, a malicious invited member, a viewer trying to become an editor/admin, compromised provider/model responses, hostile financial text, replayed webhooks and a compromised administrator trying to use configurable SMTP as an internal-network probe.

The host/operator, PostgreSQL administrator, process environment and intended household administrator remain trusted for deployment and credential configuration. Administrators have full financial access but cannot browse another user's assistant chats through the application. Granting a budget deliberately grants that category/month/currency's full household summary without underlying bank transactions. External notification audiences are separate from app membership and require explicit administrator acknowledgement. Encrypted credentials protect a database-only disclosure; compromise of the running process plus APP_SECRET defeats that protection.

JSON strings may contain leading `=` safely; a future CSV exporter must add explicit formula neutralization. Model-provided links and images render only their labels/alt text, with no URL attributes or network requests. User messages remain plain text. Authenticated citation downloads are server-generated, regenerated under current permissions and marked as JSON attachments.

The compiled `test:browser:assistant-markdown` suite covers 22 hostile payloads, including HTML/script/SVG/MathML, executable URL schemes, entity-obfuscated URLs, local/remote images, reference links and code-language attribute injection. It asserts no executable DOM, navigation, popups, remote/local tracking fetches or browser storage. Depth, token-count and size limits fall back to escaped plain text. The real HTTP/PostgreSQL `test:browser:assistant-spending` suite separately verifies exact provider text in responses/private chats, anonymous denial, formatted output and unchanged authorized source totals. No live inference is involved.

## Verification limits and residual risk

- The independent added SMTP and HTTP/browser probes passed locally, including real Chromium desktop/mobile rendering. The complete integrated run, build, syntax/format and browser results are recorded in [verification](verification.md); test totals are not substituted for the attack coverage above.
- Root verification reported zero runtime and full dependency audit advisories at assessment time. Audits only cover known advisories, not all exploitable dependency behavior. Pinning/updates and future advisories remain operator responsibilities.
- Docker packaging was reviewed (non-root runtime, no credentials/default master key, secret/dump/node_modules exclusions, shared modules included). Both Compose options parse. Full production image build/runtime could not be verified because the environment could not download the base image; static packaging checks are not container runtime tests.
- Live APP_ORIGIN requires HTTPS and live cookies are Secure; proxy headers never replace session identity. Optional `TRUST_PROXY` now resolves client IPs only through explicitly trusted IP/CIDR peers (plus loopback), walking a bounded X-Forwarded-For chain right to left; untrusted peers cannot choose their rate-limit key. The local HTTP server is intended behind a trusted HTTPS reverse proxy. Real TLS termination, certificate renewal, firewall routing, browser HSTS behavior over deployed HTTPS and proxy configuration were not tested. Restrict backend port exposure. App-origin policy is not a network firewall. An untrusted proxy or malformed chain shares the immediate peer’s IP authentication rate bucket. See [trusted proxies](reverse-proxy.md) for the Caddy/cloudflared boundary and deployment checks.
- CSP permits inline styles needed by the UI, but no inline scripts. The allowed application bundle remains trusted. No external scanner, fuzzing campaign, cryptographic formal verification, browser-engine exploit analysis or sustained denial-of-service test was performed.
- Scrypt concurrency and auth/provider budgets bound work; the service still needs normal reverse-proxy connection/body/time limits and host resource monitoring. Limited IP rate controls do not prevent distributed attacks. No MFA/SSO is implemented.
- Public SMTP is a deliberate administrator capability. DNS pinning and TLS reduce SSRF exposure; provider routing changes can cause safe delivery failures. DNS lookup timeout stops awaiting results but cannot necessarily cancel the OS resolver. Notifications are at-least-once; a crash after remote acceptance can duplicate a delivery. An already in-flight external send cannot be recalled.
- No provider/webhook/account entitlement or real Telegram/SMTP delivery was tested. Provider mock contract checks do not prove every model/region is compatible. Model prose can be wrong or influenced by untrusted descriptions even when authorization/tool bounds hold; inspect backend-derived citations. Cancellation is best-effort and cannot guarantee no provider cost. No blanket zero-retention claim is made.
- Permission checks cannot erase data already downloaded, screenshots, copied model responses or a response already delivered before revocation. New calls and in-flight assistant/report boundaries recheck access; deployment/process administrators retain host/database access.
- Private chats are temporary process memory, not encrypted persisted history; restart/expiry removes them. APP_SECRET must be backed up separately, trusted backups/access logs must not capture bearer links or sensitive payloads, and SMTP/provider accounts need least-privilege configuration outside this app.

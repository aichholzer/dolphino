# Read-only household assistant

Open the Assistant button to use the right-hand panel. An administrator must first save the shared OpenAI or Bedrock connection in **Settings → AI features**, select the assistant model, acknowledge financial-data sharing, and explicitly enable it. Classification uses that same connection while retaining its own model, enablement and limits; it cannot implicitly enable the assistant. Unconfigured service shows a setup message, never simulated answers.

The assistant receives no database connection, credentials, SQL executor, arbitrary URL fetcher, or mutation tools. Server-owned read services apply the signed-in user's current grants before retrieving or calculating anything. Administrators have full financial access; members have only explicit account grants and separately granted budget totals. Budget access does not expose underlying transactions. The assistant cannot change finances, settings, membership, send notifications, or browse the web.

## Tools and supporting evidence

| Tool                   | Authorized coverage                                                                                                                             |
| ---------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------- |
| `finance_dates`        | Authoritative local today, deterministic relative/custom ranges and DST-aware UTC bounds; no financial records                                  |
| `finance_categories`   | Authorized display names, stable category keys and archived categories; bounded lookup with explicit ambiguous/no-match results                 |
| `finance_accounts`     | Account details, source balance snapshots and freshness                                                                                         |
| `finance_transactions` | Date/account/category/merchant/amount/status/kind search and bounded pagination                                                                 |
| `finance_transaction`  | One transaction, splits and local correction within account permission                                                                          |
| `finance_aggregate`    | Exact income/expenses/net and pending/transfer amounts, grouped by month/category/merchant/account; rankings and prior equal-period comparisons |
| `finance_budgets`      | Granted monthly budgets, allocations, rollover and overspend alerts; no underlying account disclosure                                           |
| `finance_quality`      | Permitted account import coverage and reconciliation limitations                                                                                |
| `finance_report`       | Downloadable exact aggregate report, regenerated under current permissions                                                                      |

Amounts and comparisons are computed by backend integer arithmetic, not by asking the model to add displayed rows. Currency is required; currencies are never converted or combined. Report downloads are authenticated JSON, not public links. Tool provenance includes filters, timezone, currency, generation time, coverage and truncation. Inspect supporting evidence: natural-language model output can still be mistaken. See [tool contracts and financial policy](assistant-tools.md).

Each question captures one server timestamp, local today in the configured household IANA timezone, the household currency and common calendar boundaries. All of its model/tool rounds use that same clock; a follow-up question refreshes it, including across local midnight. Location is deployment configuration, never guessed physical location or GPS. `finance_dates` and the optional aggregate/search `dateRange` use the same deterministic resolver. Yesterday is the previous local date; last week is the previous complete Monday–Sunday; last month is the previous complete calendar month. `last_n_weeks` is a rolling N×7 local-day range including today (partial); `previous_n_months` selects complete months. The assistant must state that choice or clarify an ambiguous rolling/complete-period request. Custom inclusive dates and arbitrary bounded counts are supported without a question-specific response. Provenance and the answer's source display show the actual dates/timezone used. UTC start-inclusive/end-exclusive timestamp bounds account for DST; ledger date labels are never shifted to host UTC.

A category aggregate accepts an exact stable key, display name or an unambiguous eating-out synonym. Multiple matches require clarification; unknown categories, including unresolved provider IDs, never silently become zero spending. Category grouping includes display labels. Download queries retain resolved stable keys and absolute dates across renames, archival and later days. Spending uses the existing reporting engine: matching split portions, posted refunds, corrections and frozen-account history are included; pending spending, transfers, opening balances, adjustments, voided entries and deleted-account history are excluded according to the same policies as reports.

## Privacy, limits and operations

Chats are private to their owner, including against other administrators through the app. They are held only in this server process for 30 minutes and disappear on restart; 25 questions per chat and ten chats per user. Permission revisions invalidate old context even when the same grants are later restored. Shared connection or assistant configuration changes invalidate older context and require a new conversation. Do not run multiple app replicas without sticky sessions; conversation persistence is deliberately outside this MVP.

Retrieved authorized financial data and the user's question are sent to the chosen provider. OpenAI uses Responses with `store:false`, which is not a zero-retention guarantee. Bedrock retention depends on the model/region and AWS logging configuration. No silent provider fallback is used. See [provider contracts and privacy](providers.md).

There is no per-user request allowance and no output token cap. Each answer is bounded at eight model rounds, 24 tool calls and three minutes, with 60 seconds per provider call, 128 KiB model context and 64 KiB responses/results. Selections cover at most 366 days and 10,000 matching transactions; excess fails with a narrowing request rather than incomplete totals. These are request/size limits, not a guaranteed currency-denominated cost cap; set provider billing limits too.

The last configured round is reserved for answering from existing results, without increasing any limit. OpenAI uses [`tool_choice: none`](https://developers.openai.com/api/docs/guides/function-calling). Bedrock retains native Converse tool/reasoning history and tool definitions because its [ToolChoice API](https://docs.aws.amazon.com/bedrock/latest/APIReference/API_runtime_ToolChoice.html) has no portable `none` option; a final-answer instruction is enforced by refusing any additional tool execution. A model that still requests tools receives a recoverable error, not an extra paid round or a fabricated total. A one-round setting cannot both retrieve data and generate a model answer.

Provider/execution errors have a reference ID. Server diagnostics record only that ID, provider kind, execution phase, round/tool counts and the last authorized tool name. They exclude questions, arguments, results, financial values, account/category names, credentials and raw provider errors. Failed turns do not append partial conversation history; the user can retry. Missing or ambiguous category results remain explicit limitations even if a model attempts to turn them into a zero total.

Stop aborts subsequent work and requests cancellation from the provider best-effort; it cannot guarantee no inference cost. Responses are delivered as a complete reply with a busy state, not token streaming. Provider errors stop the turn without automatic retries. Model compatibility requires the administrator's explicit synthetic tool-use test; it may incur a small inference charge. Basic credential tests do not invoke a model. Bedrock access must already be authorized; dolphino does not subscribe to models or accept terms.

Tests cover provider contracts, permission changes, forged tools, report ownership, cancellation and UI flows with mocks and fictional data.

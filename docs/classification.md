# Classification and optional suggestions

dolphino applies manual corrections/splits first, then merchant rules and useful provider categories. Accepted AI categories sit below these sources and remain separate from manual overrides with an audit entry. Unchanged provider refreshes preserve an accepted AI category; substantive source changes invalidate it. Transfers and ambiguous source-identity/kind reviews are never automatically classified.

Configure `LLM_BASE_URL` (HTTPS OpenAI-compatible API base), `LLM_MODEL`, and server-side `LLM_API_KEY` or `LLM_API_KEY_FILE` to enable optional AI assistance. Choose a small inexpensive model supporting JSON responses. No provider is configured by default. Credentials never enter frontend responses or job records. No live provider call is needed for setup or tests.

Once fully configured, the background worker checks every 30 seconds and automatically queues unresolved posted transactions, including previously imported unresolved records. `LLM_AUTO_CLASSIFY=false` disables scanning and pauses existing automatic jobs; manual suggestions remain available. Pending transactions, existing manual corrections, matching rules, useful provider categories, internal transfers and ambiguous reviews bypass automatic AI work. Successful suggestions remain in the review workflow and can be retrieved using the transaction editor's suggestion action.

**Automatic application is disabled by default.** Explicitly set `LLM_AUTO_APPLY=true` to permit applying automatic-job suggestions. Categories must belong to the configured category list and must not be `Uncategorized`. Under the same database lock used for ledger mutations, dolphino rechecks the source evidence, eligibility, rules, provider category and manual overrides. Stale or unresolved suggestions fall back to review without replacing those classifications. Accepted AI classification recalculates persistent budget alerts in the same transaction. On-demand jobs always return a suggestion for review.

Only the first 120 description characters (long digit sequences redacted) and available category labels are sent. The model receives no amount, date, account identifier, bank balance, or transaction ID. Merchant descriptions and custom category labels may still be sensitive; configuring a provider permits sending these selected fields. Requests use a 15-second timeout and a 150-output-token limit. Financial values remain local even though they participate in job deduplication fingerprints.

Jobs persist in PostgreSQL and are keyed by mode, canonical transaction ID, and a fingerprint of source fields, category list, endpoint, model and a one-way credential digest. Concurrent workers share jobs and serialize provider calls (concurrency one across application instances using the same database/schema and mode). `LLM_BATCH_SIZE` defaults to 5 jobs per tick (maximum 20). `LLM_DAILY_REQUEST_LIMIT` defaults to 20 attempts per UTC calendar day (maximum 1000), shared by manual and automatic requests and all instances. Reservations are persisted before network I/O; failures and process crashes consume the allowance. This bounds request counts, not a guaranteed monetary price; provider pricing remains the operator's responsibility. Exhausted daily allowance leaves work pending until the next UTC day.

Pending jobs survive restarts and retry with exponential delays starting at one minute, honoring `Retry-After`, for at most five attempts per retry cycle. Errors persist a fixed safe code, never response bodies or credentials. The automatic scanner never resets failed jobs. Explicitly using the editor's suggestion action retries a failed job with a new bounded cycle, subject to the same daily limit. Configuration or substantive source changes create a fresh job identity. Successful suggestions are cached. Automatic acceptance applies only to automatic-origin jobs; an explicit request for a pending automatic job converts it to manual review.

Imported data, manual edits and budgets remain usable throughout provider downtime. Queue records, usage counters and audit history are included in full PostgreSQL backups. There is no bulk AI job-management UI or external alert delivery in this MVP; review and retry are per transaction.

# Assistant configuration and data sharing

The assistant and classification use one administrator-managed OpenAI or Amazon Bedrock connection in **Settings → AI features**. Enter credentials once in the shared connection form; the assistant has its own model, enable switch, data-sharing acknowledgement and cost limits. Configuring or enabling classification does not enable the assistant. Provider/region metadata is stored as `ai.provider`, feature configuration as `ai.assistant` and `ai.classification`, and credentials in encrypted `ai.*` slots. APP_SECRET remains the separately backed-up encryption key. See [shared settings and upgrade behavior](ai-settings.md).

For Bedrock, save the shared permanent access key/secret and supported region without choosing a model. One saved-credential catalog automatically populates both model pickers after saving, opening AI features, reloading or restarting. Blank write-only inputs preserve the saved credentials and do not prevent discovery; no second assistant credential entry is needed. Select a model for each feature from the dropdown, grouped by provider, then explicitly save that feature's controls. Discovery failure is retryable without re-entering keys. Listing never enables a feature or establishes account access or Converse/tool compatibility. OpenAI model IDs remain manual. Temporary AWS credentials and session tokens are unsupported. No app code grants model access, accepts model agreements or subscribes to a model. See [provider access restrictions](providers.md).

Changes to shared provider, region or credentials pause both features. A provider change clears incompatible model selections and resets the assistant sharing acknowledgement; same-provider credential/region changes preserve models, consent and all feature limits for review before re-enabling. Secret fields are write-only: omitted/blank values preserve, `null` explicitly clears. Unresolved older separate profiles require an explicit choice of a readable profile or complete replacement credentials; blank fields cannot silently resolve a conflict. Unreadable or retired version 1/2 envelopes are never decoded or recovered by restoring APP_SECRET. Those rows remain untouched until a successful explicit resolution transaction replaces the old AI configuration. Missing/wrong APP_SECRET fails credential use closed while imported data and manual work remain usable. See [upgrade recovery](upgrading.md).

Administrators must explicitly acknowledge data sharing before enabling the assistant. The user-facing disclosure explains that questions and permitted account/budget summaries may leave the homelab for the selected provider. Do not enter passwords, API keys or other secrets in questions. The assistant is read-only: no mutation tool for transactions, classifications, budgets, users, grants, integrations, notifications or settings is exposed. Local resource grants remain authoritative; a model request does not grant extra access. A budget grant may explicitly authorize a household category aggregate without transaction access, as documented in [household permissions](household-auth.md).

Limits are independent of classification:

| Setting                                 | Default | Allowed range |
| --------------------------------------- | ------- | ------------- |
| Provider requests per user per UTC day  | 10      | 1–100         |
| Tool calls per question                 | 4       | 1–8           |
| Provider rounds per question            | 3       | 1–4           |
| Maximum output tokens per provider call | 1,024   | 128–2,048     |

Multiple provider rounds consume multiple requests. Limits bound activity rather than guaranteeing a currency-denominated price; provider pricing, context size and model behavior affect cost. Configuring a model does not prove availability or tool-calling compatibility. Development uses mocked providers and synthetic settings exclusively. The explicitly requested **Test model** action exercises the actual assistant tool-calling contract: one fixed fictional summary tool and one follow-up response, at most two provider calls with at most 256 output tokens each (or the lower configured token cap). It reads no household finance data, can incur a small inference charge, and requires explicit cost acknowledgement. It does not enable the assistant.

## Provider retention and logging

OpenAI requests set `store:false`; that setting is **not a zero-retention guarantee**. Abuse-monitoring logs and organization/project data controls have separate policies and eligibility. Review the selected endpoint's current [OpenAI data controls](https://developers.openai.com/api/docs/guides/your-data) before enabling; dolphino does not enroll an account in special retention programs or change provider policies.

For Bedrock, administrators must check the selected model's data handling, AWS region and any cross-region inference profile. Account-level invocation logging can record request/response data in CloudWatch Logs or S3 when configured; dolphino does not enable, disable or delete that logging. Review [Bedrock invocation logging](https://docs.aws.amazon.com/bedrock/latest/userguide/model-invocation-logging.html) and [Bedrock data protection](https://docs.aws.amazon.com/bedrock/latest/userguide/data-protection.html), as well as applicable model terms. Do not infer that an encrypted local credential means a provider receives no financial content.

The admin settings response contains masks/configured state, disclosure and limits, never plaintext credentials. The ordinary-user status omits secret masks, credential metadata and limits; it exposes only provider/model, configured/enabled state and a safe disabled reason. Application conversation storage/deletion behavior is documented by the assistant feature; provider-side retention remains separate from deleting local records.
